# Agent Rules

Shared policy for every agent working in this repository — architect, implementation
workers, and reviewers. Task prompts should reference this file rather than restating it.

## Git

- Use the repository's existing Git identity exactly as configured.
- Never set or override `user.name` / `user.email`. Never pass `--author`.
- **No AI attribution anywhere** — not in commit messages, comments, docstrings, or file
  headers. No `Co-Authored-By: Claude`, `Co-Authored-By: Codex`, "Generated by",
  "Generated with", "AI-generated", "agent-generated", or equivalent.
- Commit messages describe only the code change, in normal engineering language. Never
  mention Claude, Codex, LLMs, agents, or automated generation.
- Workers create **local commits only**, on their assigned branch, in small logical steps.
- Workers never push, open a PR, merge, rebase, cherry-pick, force-reset, force-push, or
  rewrite history. The architect integrates; the repository owner pushes.
- Every worker reports its final local commit hash.

## Multi-agent ownership

- Each worker runs in its own isolated git worktree on its own branch.
- **One writer owns a file or module area at a time.** Never edit a file owned by another
  worker without explicit coordination through the architect.
- Shared contracts — database schema, ORM models, cross-worker interfaces, shared
  configuration — change only with architect approval.
- If a task appears to require a shared-contract or schema change, **stop and report the
  requirement with its justification. Do not make the change.**
- The same rule applies to any file outside the worker's stated ownership list: stop and
  report rather than editing.
- Before finishing, verify `git diff --name-only main` contains only owned files.

## Secrets

- `.env` files are gitignored and hold real credentials. Never stage, commit, print, or
  echo their values, and never copy a value from one into code, tests, fixtures, logs, or
  a report.
- No secret may appear in source, test fixtures, commit messages, log output, error
  messages, or worker reports.
- All configuration comes from environment variables. Placeholders belong in
  `.env.example`; real values never enter the repository.
- Credential-like settings use a secret-wrapping type so they cannot leak through a repr
  or traceback.

## MVP and deployment posture

- Prioritize a working, deployable MVP over architectural completeness.
- Priority order: working end-to-end flow → correct, evidence-backed results → simple and
  debuggable → deployable → maintainable → optimization only when real usage justifies it.
- Avoid unnecessary infrastructure: no queues, background workers, Redis, cron, caching
  layers, microservices, or approximate vector indexes until a real requirement exists.
- The deployed MVP read path targets Vercel: short-lived, stateless serverless execution.
  No long-lived processes, no in-memory state carried between requests, and no filesystem
  persistence in any deployed request path.
- No hardcoded `localhost`, `127.0.0.1`, machine-specific paths, or port literals in
  application code. Development defaults belong in `.env.example`.
- Local Docker Compose is development and integration infrastructure, **not** the
  production architecture.
- Scripts that write files take the path as an argument with a relative default.

## Testing responsibility

Tests are owned, not duplicated. Each role runs its own layer and trusts the others:

- Whoever implements a change runs the unit and integration tests for the code they own.
- Integration of parallel work verifies contracts and boundaries, not the whole suite.
- The full suite runs once after integration.
- Review runs adversarial and risk-targeted tests, not a rerun of everything.

Unit tests must pass with no database and no network. Tests that need PostgreSQL are
marked `integration` and skip cleanly when it is unavailable.

## Worker completion report

Finish with a concise report containing **only** these fields:

- status
- branch
- commit hash
- files changed
- behavior implemented
- tests: command + result counts
- assumptions
- remaining risks
- requested shared-contract changes

Do not include implementation narration, step-by-step reasoning, or terminal
transcripts unless explicitly requested.
